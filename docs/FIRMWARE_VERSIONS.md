# PS4 system software versions

The UEFI firmware (EDK II + `Ps4Pkg`) does not depend on the system software version: it runs after OrbisOS
is gone and drives the hardware directly. Only the **directboot stage** depends on it, because it calls into
the running OrbisOS kernel (allocators, `smp_rendezvous`, `wlanbt`, the `icc_query_nowait` shutdown hook)
and patches two of its instructions.

## How the stage picks a version
`src/directboot/fwtable.h` holds one row of kernel offsets per version (generated by `tools/mkfwtable.py` from
the PS4 Linux loader's tables in `reference/linux-loader-zip`: `magic.h` and `fw_offsets.h`). At arm step 0
(`src/directboot/arm.c`, `fwsel.c`) the stage, without writing anything:
1. finds the kernel base from `IA32_LSTAR` and checks the syscall entry is there;
2. tests every row: each function it calls must start with a frame prologue, kmem_alloc's protection operands
   and the pstate argument must have the expected instruction shapes, the first ≥ 14 bytes of
   `icc_query_nowait` must decode into whole position-independent instructions (they are copied into the hook
   trampoline), then `kernel_map` and the DMAP globals must hold plausible values. Code sites (within the
   first ~5 MiB of the kernel image) are checked first; data sites are read only for a row whose code checks
   all passed;
3. requires **exactly one** matching row and reports it;
4. **refuses to arm** if the row has no `phys_avail` offset (see below). This happens before the DMAP proof,
   because that proof dereferences an address built from the row's values;
5. for an armable row, proves the DMAP globals through the page tables (CR3).

The receiver log shows the matched version, whether its row is verified, the patch-site values and how many
bytes the hook displaces. A kernel that matches no row (or several) is refused.

## Status per version
| Version(s) | Row | phys_avail | Stage behaviour |
|---|---|---|---|
| **9.00** | verified (kernel dump + hardware) | known (`0x2216a80`) | arms and takes over (hardware-proven) |
| 5.05, 6.72, 7.00, 7.50, 8.00, 8.50, 9.03, 9.60, 10.00, 10.50, 11.00, 11.02, 11.50, 12.00, 12.50, 13.00, 13.02, 13.50, 13.52, 14.00, 14.02 | unverified (community offsets from the Linux loader) | unknown | recognised and checked, **not armed** (reports, then stops before the first write) |

Versions that share a kernel with a listed one (for example 9.04 with 9.03, as the loader's comments note) are
matched by the same row when their code is identical; otherwise they match no row and are refused.

`phys_avail` matters because the memory map handed to EDK II marks RAM that OrbisOS still owns (firmware
areas, GPU-shared memory) as reserved using OrbisOS's own free-memory list. Without it the stage would have to
guess, and EDK II could allocate memory that is still in use.

## Bringing up another version
1. **Kernel dump** of that version, from a console running it (a dumper matched to that version; the 9.00
   dump's sha256 is in `docs/notes/LEDGER.md`).
2. **Check the row:** `make hosttest KDUMP=<dump>`. Edit `tools/fwsel_hosttest.c`'s expectation (it asserts the
   matching row is 9.00) or run the binary directly; the per-row list must show `ok` for exactly that version.
3. **Find `phys_avail`:** on 9.00 it is the array `hammer_time`/`getmemsize` stores into with a `lea` next to
   `dump_avail` (`src/k0probe/README.md`); locate the same code in the new dump. The read-only `k0probe`
   payload can confirm it on the live console (its 9.00 gates would need the same table treatment).
4. Add the value to `tools/mkfwtable.py` (per-version `phys_avail`), run `make fwtable stage`, test in QEMU
   (`make qemu` covers the UEFI side only; QEMU does not run OrbisOS), then a filmed hardware run.
5. After a successful hardware run, mark the row verified in `mkfwtable.py`.

## Limits
- Only 9.00 has been run. Every other row's offsets are unverified until step 2 passes on a dump.
- The stage enters ring 0 through syscall 11, which the jailbreak must leave installed (WebKitty's kernel patch
  does this for 7.00–9.60). With other jailbreaks this depends on what they install.
- Hardware: PS4 "Fat" with the Aeolia southbridge only. Slim/Pro (Belize/Baikal) differ below OrbisOS and are a
  separate porting task.
- The read-only diagnostic payloads (`src/diag`, `src/k0probe`) still check for 9.00 only.
