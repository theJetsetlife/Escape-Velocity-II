# Escape Velocity II — native UEFI firmware for the PS4 Fat

Boots a real UEFI environment (EDK II, UEFI Shell) on a PlayStation 4 "Fat" (Aeolia southbridge) with no Linux in
between: a ring-0 **directboot stage** takes the machine over from OrbisOS and hands it to an **EDK II Universal
Payload** built from unmodified upstream edk2 plus `Ps4Pkg/`. Proven on hardware on system software **9.00**; the
stage recognises 22 versions (5.05–14.02) and arms the verified ones.

Goal of the current work: 64-bit OS loaders, all 6 GiB of system RAM, NTFS, one-command logging, more system
software versions, and Windows 10 booting from an external USB drive.

**Start with [HANDOFF.md](HANDOFF.md)** — current state, what is proven on hardware vs only in QEMU, the rules
learned the hard way, and the next steps.

## Status at a glance

|---|---|
| Delivery (WebKitty → GoldHEN slot) → ring 0 → takeover → EDK II → UEFI Shell on screen | **proven on hardware** on 9.00 (stage `ff86e20d` + UEFI `5c32a84d`, `prebuilt/hw-verified/`) |
| USB (xHCI ×3), SATA, SD, UART, DualShock 4 as keyboard, Marvell Yukon Ethernet | built + QEMU-tested (`prebuilt/io-build/`, UEFI `d7a705d2`); **not yet run on hardware** |
| 6 GiB RAM (2 GiB VRAM carve), DMA bounce < 2 GiB, NTFS (read-only), `ps4log` | built + QEMU-tested; **not yet run on hardware** |
| System software versions | stage selects kernel offsets per version at run time: 22 rows (5.05–14.02) from the PS4 Linux loader, cross-checked against OpenGoldHEN (16 versions, 80/80 values agree), 13 further point releases share a row's layout. **9.00 arms; the others are recognised and refused** until their `phys_avail` is known. Multi-version stage checked against the 9.00 kernel dump, **not yet run on hardware** — [docs/FIRMWARE_VERSIONS.md](docs/FIRMWARE_VERSIONS.md) |
| Windows 10 | Setup reaches its first screen in QEMU through this firmware with the PS4 DSDT; needs a working IOAPIC (open problem) — [docs/WINDOWS10.md](docs/WINDOWS10.md) |

## How version support works
The UEFI firmware does not depend on the system software version; only the stage does, because it calls into the
running OrbisOS kernel. `src/directboot/fwtable.h` (generated by `tools/mkfwtable.py`) holds one row of kernel
offsets per version. At its first, read-only arm step the stage accepts exactly one row whose code sites all have
the expected instruction shapes, refuses versions whose `phys_avail` is unknown, and writes nothing before every
check has passed. Adding a version takes a kernel dump of it, `phys_avail` from that dump, and one hardware run —
steps in [docs/FIRMWARE_VERSIONS.md](docs/FIRMWARE_VERSIONS.md).

## Layout
| Path | What |
|---|---|
| `src/directboot/` | the stage: GoldHEN-slot payload, version selection (`fwsel.c`, `fwtable.h`), ring-0 arm, ICC hook, OrbisOS takeover, memory map, UPL load |
| `src/upl_load.c`, `src/upl_hob.h` | ELF Universal Payload loader + HOB builder (shared with the QEMU harness and host tests) |
| `src/diag/`, `src/k0probe/` | read-only diagnostic payloads used to measure the machine before the takeover existed (9.00 only) |
| `Ps4Pkg/` | all PS4 EDK II code: drivers, libraries, `mkplatform.py` (derives the platform DSC/FDF from upstream) |
| `qemu/` | QEMU harness that imitates the PS4 handoff (stub + `h64`) — the regression gate for the UEFI side |
| `tools/` | host tests, offset-table and DSDT generators, PC-side receiver, WebKitty server helper, deploy, Windows tools |
| `server/` | docker compose for the PC side of a hardware run |
| `scripts/setup-edk2.sh` | fetches the pinned upstream edk2 (commit `2970e569`) |
| `prebuilt/` | known binaries with their status ([prebuilt/README.md](prebuilt/README.md)) |
| `docs/` | architecture, build, testing, hardware runs, system software versions, Windows 10; `docs/notes/` = original engineering notes |
| `reference/` | third-party and proprietary reference material (see [reference/NOTICE.md](reference/NOTICE.md)) |

## Quick start
```sh
make setup                  # pinned upstream edk2 + BaseTools (once; ~1 GB)
make upl                    # out/upl-ps4.elf
cp server/.env.example server/.env && $EDITOR server/.env    # PC_IP, WEBKITTY_DIR
make stage                  # src/directboot/directboot.bin (PC address built in)
make hosttest               # host unit tests (KDUMP=<9.00 kernel dump> adds the version-selection dump check)
make qemu                   # QEMU regression matrix -> MATRIX: PASS
make fwtable                # only after changing tools/mkfwtable.py: regenerate the offset table
```
Then [docs/HARDWARE.md](docs/HARDWARE.md) for a PS4 run. Details: [docs/BUILD.md](docs/BUILD.md),
[docs/TESTING.md](docs/TESTING.md), [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md),
[docs/FIRMWARE_VERSIONS.md](docs/FIRMWARE_VERSIONS.md).
